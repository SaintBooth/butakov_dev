On October 16 I sat down to figure out why my site gets almost no search traffic. I opened Yandex Metrica and got a placeholder: "Metrica is temporarily unavailable." Webmaster showed the same. Direct, Yandex's ad platform, was down too, according to the news. The only place I could still see my own traffic for those days was the Umami instance on my own server, so the traffic sources report came from there, through its API, in a couple of minutes.

The short version: if your analytics lives on someone else's infrastructure, their outage blinds you for as long as it lasts, and conversion-optimized ad campaigns lose their signal at the same time. A second counter that writes visits and goals into your own database fixes the first problem. Server-side offline conversions fix most of the second.

## What happened in October 2026

Between October 8 and 11, 2026, Yandex shut down three of its five data centers, citing drone attacks and a fire. According to [industry reports](https://seo.ru/news/kabinety-direkta-metriki-i-vebmastera-nedostupny-posle-atak-na-data-centry-yandeksa/), Metrica data started arriving with gaps on the 8th, and from the 11th the Metrica, Direct and Webmaster dashboards stopped opening. Search, Maps and Taxi partly came back that evening. Analytics and ads stayed down.

I did not see this coming. I set Umami up on October 13, mid-outage, because I wanted session recordings and heatmaps without handing data to a third party. It became my backup counter by accident.

## What breaks when one tool holds all your analytics

I am keeping Metrica: Direct needs it, and it does its job. The trouble starts when its infrastructure fails, because everything goes at once.

Reports go first. Even if the counter keeps collecting in the browser, there is nowhere to look at the data, so every decision about the site in those days is made blind.

Ads are worse. Direct's conversion-optimizing bid strategies learn from Metrica goals. When goals stop arriving, a strategy reads it as a conversion drop rather than an outage and adapts to a picture that is not real.

Then there is the loss that happens every day, outage or not. `mc.yandex.ru` is on every major block list, from uBlock Origin to AdGuard to browsers' built-in tracking protection. A visitor running one of them does not exist for Metrica. How many such visitors you have depends on your audience; with developers and B2B buyers it is noticeably more.

## Picking a self-hosted tool

| Tool | Runs on | License | Cookies | Best for |
| --- | --- | --- | --- | --- |
| Umami | Node.js + PostgreSQL | MIT | none | sites and small projects: visits, sources, goals |
| Plausible CE | Elixir + PostgreSQL + ClickHouse | AGPL-3.0 | none | the same, needs a stronger server for ClickHouse |
| Matomo | PHP + MySQL/MariaDB | GPL-3.0 | yes by default, can be disabled | a full replacement with e-commerce, heatmaps, tag manager |
| GoAccess | C, reads web server logs | MIT | no JS at all | counting every request, no in-page events |

I needed something that would sit on ordinary Node.js hosting next to the site and get by with one PostgreSQL database. Umami fit, and the MIT license settled any question about what I can do with it. For an online store that needs sales funnels and heatmaps from day one, I would look at Matomo instead.

## How my setup works

### A separate subdomain on my own server

Umami runs as its own site on a subdomain, on the same hosting as the main site, with its own PostgreSQL database. Visit data never leaves the server. Shared hosting made the install harder than I expected; on a VPS with Docker, the official image starts with a single command.

The dashboard requires authentication, and only the tracker script and the event endpoint are reachable from outside. An analytics dashboard left open on a public address shows anyone your whole traffic picture, so lock it down before anything else.

### Renamed endpoints against ad blockers

Block lists know Umami's default paths, `/script.js` and `/api/send`. Umami lets you rename both through its own environment variables, no Nginx proxy required:

```bash
# TODO: pick your own names, do not copy them from articles
TRACKER_SCRIPT_NAME=<your-name>.js
COLLECT_API_ENDPOINT=/api/<your-path>
```

On a subdomain of your own site, these requests look like ordinary first-party traffic. Keep the names out of public write-ups: once a path is published, it can land on a block list.

### One function sends every goal to both systems

With goals fired from different places in the code, Metrica and Umami would drift apart sooner or later. So the site has one entry point:

```ts
export function track(event: AnalyticsEvent, data?: EventData) {
  // visitor declined analytics, or this is a service page
  if (isTrackingBlocked()) return;
  const payload = EVENT_SCHEMAS[event].parse(data ?? {});

  // Umami loads deferred: queue events until its script is ready
  if (window.umami) window.umami.track(event, payload);
  else if (pending.length < MAX_PENDING) pending.push([event, payload]);

  if (typeof window.ym === 'function') window.ym(YM_ID, 'reachGoal', event, payload);
}
```

Every event is validated against a schema, so a typo in a goal name breaks the build instead of a month of stats. If Metrica fails to load because it is blocked or down, the goal still reaches Umami, and the reverse holds too.

### What must never reach analytics

Some pages carry a secret in the URL: an access token, a key in a link. Metrica records full URLs, so that token would sit in reports for anyone with access to the counter. On those pages neither counter loads, and Umami has an extra `data-before-send` hook that cancels any hit whose URL matches a blocked pattern. Password reset links, email confirmations and document links with keys deserve the same check on your site.

### Cookies and consent

Umami sets no cookies. It derives the session on the server from a hash of the website ID, IP, user agent and a salt that rotates monthly by default (adjustable with `SALT_ROTATION`). The IP itself is not stored, and one person's visits cannot be linked across months.

I kept the consent banner anyway, because Metrica runs alongside and does set cookies. If a visitor declines, neither counter loads and no goal is sent.

## Keeping ad conversions flowing

A second counter saves your reports, not your ads: Direct only sees Metrica goals. To stop ads depending on a browser script, hand conversions to Metrica from the server as offline conversions. Store the `yclid` click ID (or Metrica's `ClientId`) with each lead, and when the CRM marks a sale, upload a CSV:

```csv
Yclid,Target,DateTime,Price,Currency
1837492018473920190,ORDER_PAID,1760600000,15400,RUB
```

`DateTime` is a Unix timestamp and must be in the past, or the API rejects the file. It goes to `POST https://api-metrika.yandex.net/management/v1/counter/{counterId}/offline_conversions/upload` as multipart/form-data and shows up in reports [within three hours](https://yandex.ru/dev/metrika/ru/management/offline-conv). During an outage like October's you cannot upload either, but nothing is lost: conversions and click IDs wait in the CRM and go out once the API is back. My own site does not sell through a cart, so I have not set this up yet; for a store with a CRM and Direct campaigns, it is the next step after a second counter.

## FAQ

**What should I do when my analytics provider goes down?**
Confirm it is a provider-side outage, mark the period as incomplete, leave ad settings alone for those days, and set up a second counter that stores data on your own server.

**Is Umami a good Google Analytics alternative?**
For visits, sources and custom events, yes: it is light, cookieless and self-hosted. For e-commerce funnels, heatmaps and a tag manager, Matomo is closer to a full replacement.

**Does Umami need a cookie banner?**
Umami sets no cookies, but if your site also runs counters or ad pixels that do, you still need consent for those.

**How do I hide Umami from ad blockers?**
Serve it from a subdomain of your site and rename the default paths with `TRACKER_SCRIPT_NAME` and `COLLECT_API_ENDPOINT`, using names you do not publish anywhere.
